# 并发、名额与多活动架构

## 为什么当前不使用 Redis

本系统面向单所学院、单场约 150 名学生的抢选。名额的权威数据是 SQLite 中的
选择记录，不是内存计数器或缓存。

每次抢位都在同一个 `BEGIN IMMEDIATE` 事务中完成以下操作：

1. 检查活动仍处于开放状态；
2. 检查学生尚未选择；
3. 检查专业配额和教学组总容量；
4. 写入选择记录和审计日志；
5. 一次性提交。

SQLite 在事务开始时串行化写入，数据库唯一索引阻止同一学生重复选择，
`selection_capacity_guard` 触发器又在数据库层阻止专业配额或教学组总容量超限。
因此“最后一席”是数据库原子判定，不依赖浏览器看到的剩余数字。

Redis 不适合充当本系统的名额账本：如果先扣 Redis、再写 SQLite，任何中途故障
都会形成双写不一致。当前规模加入 Redis 只会增加部署和恢复复杂度。只有以后变成
多应用副本时，才考虑用 Redis 做跨实例限流、缓存或消息广播；若达到上千并发、
多活动同时开放或需要数据库高可用，应优先把权威数据迁移到 PostgreSQL。

## 并发验收标准

- 150 名不同学生同时争抢 30 席：必须恰好 30 成功、120 返回满额冲突；
- 同一学生并发重复提交：必须只有 1 次成功；
- 不允许出现超卖、重复有效选择或 5xx；
- 数据库必须通过 `integrity_check`、`foreign_key_check` 和名额触发器检查；
- SQLite 数据卷必须位于 VM 本机磁盘，不得直接放在 SMB/NFS 上。

## 多次使用方式

系统一次只允许一个当前活动，避免学生扫错二维码或多个年级互相串场。每场活动的
生命周期为：

`关闭配置 → 开放抢选 → 关闭 → 归档并新建下一场`

“归档并新建”会在同一个数据库事务中：

- 保存活动信息、专业、教学组、配额、名单、完整选择历史和活动审计日志；
- 生成归档 JSON 及 SHA-256 校验值；
- 将旧活动标记为只读归档；
- 让旧学生会话立即失效；
- 清空当前工作区中的学生和选择；
- 可选复制上一场的专业、教学组与配额，作为下一场模板。

学号可在新活动中再次导入；后续对新活动结构或学生资料的修改不会改变旧归档。
归档只能由管理员下载，不包含激活码哈希、会话或管理员密码。

## 名单与个人激活码生命周期

名单 CSV 默认只需要“学号、姓名、专业”三列。系统为新学生生成随机 8 位个人激活码，数据库只保存基于
`APP_SECRET` 的 HMAC，不保存可恢复明文。明文仅在本次导入或重置响应中返回，管理员必须立即下载并安全下发。

- 合并更新保留文件外学生；同步名单会停用文件外学生并注销其会话，有有效选择时拒绝同步并要求先撤销；
- 批量重置或单人补发都会生成新码、注销该学生现有会话并写入审计日志；
- 个人激活码不是登录一次即销毁的 OTP，避免学生清理 Cookie 后永久无法再次进入；泄露处置依赖显式重置；
- 新活动不会复制学生或激活码，必须重新导入名单，因此每场活动拥有独立凭据；
- CSV 导出会中和电子表格公式前缀，归档不包含激活码哈希或明文。

所有会改变当前活动的请求都携带 `X-Activity-ID`。服务端取得 SQLite 写锁后才比较
请求活动与当前活动；旧标签页、旧确认框或重复请求如果跨过了活动切换边界，会返回
409，而不会误改下一场活动。学生登录、选择确认与会话写入也在线性化事务内完成。

数据库使用 `PRAGMA user_version` 管理结构版本。旧版单活动数据库首次启动时会自动
映射为第一个活动。生产更新脚本先在备份副本上执行迁移、业务行摘要对比和深度检查，
再进入短维护窗迁移正式库；正式库或新容器未通过本机检查时，不会恢复公网 Tunnel。
