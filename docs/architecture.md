# 并发、名额与多活动架构

## 为什么当前不使用 Redis

本系统面向单所学院、单场约 150 名学生的抢选。名额的权威数据是 SQLite 中的
选择记录，不是内存计数器或缓存。

同时到达的抢位先进入有界、按到达顺序处理的写入队列。单个 SQLite
`BEGIN IMMEDIATE` 事务最多批量处理 64 个请求，每个请求使用独立 savepoint：

1. 检查活动仍处于开放状态；
2. 检查学生尚未选择；
3. 检查专业配额和教学组总容量；
4. 写入选择记录和审计日志；
5. 成功请求随批次一次性提交；单个失败只回滚自己的 savepoint。

这把“每名学生一次 fsync”降低为“每批一次 fsync”，并避免数百个请求各自争用
`busy_timeout`。HTTP 写路由先执行有界队列准入，再异步等待提交，不占用 FastAPI
同步工作线程；队列为选座保留容量，低优先级登录/心跳即使突发也不能占满这些槽位。
心跳使用低优先级批量写，不会抢在选择提交之前。SQLite 在事务开始时
串行化写入，数据库唯一索引阻止同一学生产生两条有效选择，
`selection_capacity_guard` 触发器又在数据库层阻止专业配额或教学组总容量超限。
因此“最后一席”是数据库原子判定，不依赖浏览器看到的剩余数字。

学生在成功响应丢失后重放同一教学组选择，会返回既有选择和同一签名凭证；不会新增
选择或审计记录，即使管理员已在响应丢失后关闭活动也可恢复原结果。重放所需的完整
可用名额投影在写事务提交后读取，避免拖长共享写锁；改选其他教学组仍返回冲突。

Redis 不适合充当本系统的名额账本：如果先扣 Redis、再写 SQLite，任何中途故障
都会形成双写不一致。当前规模加入 Redis 只会增加部署和恢复复杂度。只有以后变成
多应用副本时，才考虑用 Redis 做跨实例限流、缓存或消息广播；若达到上千并发、
多活动同时开放或需要数据库高可用，应优先把权威数据迁移到 PostgreSQL。

## 并发验收标准

- 150 名不同学生同时争抢 30 席：必须恰好 30 条有效选择、120 返回满额冲突；
- 300 名不同学生在有 300 席时同时提交：必须 300 次成功且不出现 busy/5xx；
- 同一学生重复提交同一教学组可以幂等成功，但必须只有 1 条有效选择和 1 条创建审计；
- 不允许出现超卖、重复有效选择或 5xx；
- 数据库必须通过 `integrity_check`、`foreign_key_check` 和名额触发器检查；
- SQLite 数据卷必须位于 VM 本机磁盘，不得直接放在 SMB/NFS 上。
- 1000 人目标必须在真实外网节点重新通过登录、心跳、倒计时、选择和凭证全链路压测；
  批量写入优化本身不是容量达标声明。若仍无法满足零错误目标，再迁移 PostgreSQL。

## 多次使用方式

系统一次只允许一个当前活动，避免学生扫错二维码或多个年级互相串场。每场活动的
生命周期为：

`关闭配置/学生候场 → 教师发令 → 统一 10 秒倒计时 → 开放抢选 → 关闭 → 归档并新建下一场`

倒计时目标以 UTC 绝对时间 `selection_opens_at` 保存。手机端用响应中的 `server_now`
校正显示，但是否允许选择始终由抢位事务中的服务端时钟判定。候场在线状态使用学生
会话的 `last_seen_at`：浏览器每 5 秒发送心跳，服务端每名学生最多 15 秒写入一次，
35 秒没有心跳即从“已进入”转为“尚未进入”。心跳统计不参与名额计算。

“归档并新建”会在同一个数据库事务中：

- 保存活动信息、专业、教学组、配额、名单、完整选择历史和活动审计日志；
- 生成归档 JSON 及 SHA-256 校验值；
- 将旧活动标记为只读归档；
- 让旧学生会话立即失效；
- 清空当前工作区中的学生和选择；
- 可选复制上一场的专业、教学组与配额，作为下一场模板。

学号可在新活动中再次导入；后续对新活动结构或学生资料的修改不会改变旧归档。
归档只能由管理员下载，不包含激活码哈希、会话或管理员密码。
归档删除是另一条显式的危险操作：仅允许删除非当前的只读归档，要求当前活动版本、
CSRF 校验和二次确认，并在当前活动审计中记录被删归档的编号和校验摘要。

## 容量与配额联动

教学组总容量是该组最终可售名额，专业配额是总容量在专业之间的分配。修改教学组
总容量时，旧配额不会阻断保存；服务端在同一个写事务内先保留每个专业已经产生的
有效选择，再按现有配额权重使用确定性的最大余数法分配剩余额度。现有配额全为零时，
改按各专业活跃学生数分配。存在至少一个启用专业时，调整后的各专业配额之和等于教学组总容量，且任何配额
都不会低于该专业在该组的已选人数。若新总容量低于该组已经产生的有效选择数，
请求仍会被拒绝，因为已有结果不能被静默挤出。

## 管理员多设备会话

管理员会话允许同一账号同时保留有限数量的有效设备，支持电脑全屏投影与手机查码。
单设备退出只撤销自己的令牌；修改密码会撤销其他管理员会话。学生仍保持单会话，
重新登录或重新导入导致凭据变化时旧会话立即失效。

## 名单与个人激活码生命周期

名单导入接受 CSV、XLS、XLSX，可在一次请求中选择多个文件。每个 Excel 文件只读取首个工作表，服务端先解析并合并
所有文件，再在同一个 `BEGIN IMMEDIATE` 事务中执行合并或同步；同文件或跨文件学号重复会使整批失败。
必填列为“证件号、姓名、专业名称、学号”。证件号先规范化，再仅取末 6 位作为个人激活码；完整证件号不会落库、返回、
审计、归档或写入日志。登录校验只使用基于 `APP_SECRET` 的 HMAC；为满足管理员按需查看，系统同时保存以
`APP_SECRET` 派生密钥加密的 AES-GCM 密文。密文不进入管理大屏、归档或审计详情，
查看接口要求管理员会话、CSRF 和当前活动版本，带有限流和 `no-store` 响应，并单独记录查看审计。

名单中尚不存在的专业会在同一导入写事务内自动创建并启用，同时为全部教学组补齐零配额；已停用的同名专业会被
重新启用并写入审计。系统不会猜测新专业配额，开放就绪检查会要求管理员先完成配额设置。解析学生、创建专业、更新
凭据或同步停用中的任一步失败，专业、配额、学生和审计会一起回滚。

- 合并更新保留全批文件外学生；同步名单以本次全部文件的并集为全集，停用全集外学生并注销其会话，有有效选择时拒绝同步并要求先撤销；
- 禁止随机生成、批量重置或单人随机补发；证件末 6 位变化时重新导入名单，系统更新哈希/密文并注销该学生旧会话；
- 管理员查看明文不会改变登录凭据；当前名单中的激活码必须同时具备 HMAC 校验值和加密密文；
- 个人激活码不是登录一次即销毁的 OTP，避免学生清理 Cookie 后永久无法再次进入；泄露处置依赖重新导入权威名单；
- 新活动不会复制学生或激活码，必须重新导入名单，因此每场活动拥有独立凭据；
- 三类 XLSX 导出都会中和电子表格公式前缀，并按 WPS/Excel 打印场景统一居中、列宽和分页；完整结果覆盖所有在册学生；归档不包含证件号、激活码哈希或明文。

学生选择成功后，服务端按活动、选择、学生、教学组和记录时间生成版本化 HMAC 签名 Token 与短核验码。9:16 下载
凭证只包含抢选结果、核验码和同源核验二维码，不包含证件号或激活码。二维码 Token 放在 `/receipt` 的 URL fragment
中，不进入初始 HTTP 请求或 Referer；核验页随后以 `no-store`、`no-referrer` 请求公开核验 API。当前记录被撤销后
原凭证立即显示失效；活动归档后仅在归档快照 SHA-256 校验通过时继续核验。

所有会改变当前活动的请求都携带 `X-Activity-ID`。服务端取得 SQLite 写锁后才比较
请求活动与当前活动；旧标签页、旧确认框或重复请求如果跨过了活动切换边界，会返回
409，而不会误改下一场活动。学生登录、选择确认与会话写入也在线性化事务内完成。

数据库使用 `PRAGMA user_version` 管理结构版本，只接受全新空库或当前 schema v3 数据库，
不再包含旧库自动迁移路径。生产更新脚本先对备份副本执行版本与深度检查，再进入短维护窗；
正式库或新容器未通过本机检查时，不会恢复公网 Tunnel。
